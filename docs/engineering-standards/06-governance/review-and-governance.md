# 评审与治理规范

## 目标

定义 Code Review、架构评审、质量度量、治理职责和例外管理要求，帮助团队持续提升工程质量并控制高风险变更。

## 适用范围

适用于新系统建设、重大重构、跨系统集成、公共接口变更、数据模型变更、安全边界变更、高风险发布、质量度量和规范例外管理。

## 规范要求

- 高风险技术变更必须进行架构评审。
- Code Review 必须优先检查正确性、安全、兼容性、可观测性、测试、回滚风险和运维影响。
- 质量度量必须服务于改进决策，不得用于单一排名或脱离上下文问责。
- 规范例外必须记录规则、原因、风险、负责人、缓解措施、确认人和复审日期。
- 开发团队、Tech Lead、架构师、测试角色和运维角色必须明确治理职责。
- 重复缺陷、重复故障、长期告警和质量门禁例外必须进入治理视角。

## Code Review

Code Review 不只是代码风格检查。评审必须优先关注变更是否正确、安全、可测试、可回滚、可运维。

阻断性意见必须说明失败场景、影响范围和修正方向。非阻断性改进必须明确为可改进项，不得将个人偏好伪装成质量门禁。

提交者必须提供变更背景、范围、风险、验证方式、影响系统和必要回滚说明。评审者不得要求提交者重写与本次风险无关的大范围代码。

## 架构评审

以下变更必须进入架构评审：

- 新系统或新核心模块。
- 重大跨系统集成。
- 存储模型、数据同步或数据生命周期变化。
- 公开 API、消息契约或跨团队接口变更。
- 认证授权、租户隔离、数据保护等安全边界变化。
- 高风险迁移、框架升级或中间件替换。
- 影响发布、回滚、容量、成本或可观测性的重大调整。

架构评审必须关注目标、约束、边界、数据流、依赖、失败模式、安全、性能、可观测性、发布和回滚。

## 质量度量

质量度量必须用于发现趋势和改进机会。可关注的指标包括缺陷趋势、交付前置时间、Code Review 周期、测试稳定性、部署频率、回滚率、故障复发率、关键系统告警质量和技术债关闭率。

度量必须结合上下文解读。单个指标不得直接代表团队质量，也不得替代具体问题分析。质量度量结果必须形成可执行改进项。

## 治理职责

开发团队负责日常工程实践落地，包括编码、测试、文档、配置和发布准备。

Tech Lead 负责团队级工程质量，包括评审质量、模块边界、技术债、例外控制和质量改进计划。

架构师负责跨系统一致性、关键技术方案、高风险变更评审和长期技术路线。

测试角色负责测试策略、质量风险识别、回归范围、测试报告和发布判断。

运维或平台角色负责运行标准、发布协作、可观测性、告警、运行手册和故障处置协同。

## 例外管理

例外管理用于处理短期无法遵守规范的情况，不用于规避规范。

例外记录必须包含规则、原因、风险、负责人、缓解措施、复审日期和确认人。高风险例外必须在发布前明确沟通，并在发布后进入复审。

例外到期后必须关闭、延期或升级处理。长期存在的例外必须转化为架构、技术债或治理事项。

## 常见反模式

- 架构评审只看文档格式，不讨论风险和取舍。
- Code Review 只讨论风格，不讨论正确性和回滚风险。
- 质量指标只用于排名，不用于改进。
- 例外口头确认，没有记录和复审。
- 规范问题长期无人负责。
- 重复故障只处理单次问题，没有治理行动。

## 检查清单

- 本次变更是否需要架构评审？
- 架构评审是否覆盖边界、数据、安全、失败模式、发布和回滚？
- Code Review 是否覆盖正确性、安全、测试、可观测性和回滚风险？
- 质量度量是否用于发现趋势和改进？
- 治理职责是否明确到团队或角色？
- 例外是否记录规则、原因、风险、负责人、缓解措施和复审日期？
- 重复问题是否进入治理视角？
