# 分支与提交规范

## 目标

统一分支模型、分支命名、提交信息、合并策略和回滚追踪要求，降低长期分支漂移、提交历史不可审查和发布来源不可追溯风险。

## 适用范围

适用于所有进入仓库历史的代码、测试、文档、配置、CI、部署、规范和工具脚本变更。

## 规范要求

- 主干分支必须保持可构建、可测试、可发布。
- 长期分支只能是仓库约定的主干分支，例如 `main` 或 `master`。不得维护长期漂移的并行主干。
- 短期分支必须从最新主干、发布基线或明确 hotfix 基线拉出。
- 分支名称必须使用 `<type>/<scope>-<short-desc>` 格式，例如 `feat/auth-oidc-login`、`fix/api-response-null`、`docs/engineering-standards`。
- 分支类型必须表达主要变更意图，可以使用 `feat`、`fix`、`docs`、`test`、`refactor`、`chore`、`build`、`ci`、`hotfix`。
- 不得使用 `misc`、`temp`、`work` 等无法表达正式变更意图的分支类型。
- 提交信息必须使用 `<type>: <summary>` 格式，摘要必须说明真实变更意图。
- 单个提交应当表达一个可审查、可回滚的变更意图，不得混合无关功能、重构、格式化、依赖升级和生成产物。
- 主干和发布标签不得被强制推送或移动。

## 分支管理

单个分支应当承载一个可审查主题。发布分支只能接收与该发布相关的修复和验证。hotfix 分支必须从受影响发布标签或明确基线拉出，修复完成后必须将修复带回主干。

已合并或放弃的远端短期分支必须清理。保留分支必须能从名称或评审说明判断当前用途。

## 提交管理

允许的提交类型包括：

- `feat`：功能变更。
- `fix`：缺陷修复。
- `docs`：文档变更。
- `test`：测试变更。
- `refactor`：不改变外部行为的重构。
- `chore`：工程维护。
- `build`：构建相关变更。
- `ci`：流水线相关变更。

提交不得包含临时调试输出、个人环境文件、密钥、IDE 私有状态或未解释的大规模格式化噪音。

## 合并与回滚

合并到主干前必须完成评审、相关验证和影响说明。合并记录必须能追溯需求、缺陷、评审、测试、制品和发布信息。

回滚必须记录触发原因、回滚范围、回滚版本、验证结果和修复路径。

## 落地要求

- 代码评审必须检查分支名称、提交粒度、提交信息和无关变更。
- 影响契约、部署、数据库或生成产物的提交必须说明验证命令、生成命令或影响范围。
- `.gitignore` 是提交边界依据；已忽略文件不得通过强制添加进入提交，确需纳入时必须先修改忽略规则并说明原因。

## 检查清单

- 分支名称是否符合 `<type>/<scope>-<short-desc>`？
- 提交信息是否符合 `<type>: <summary>`？
- 单个提交是否保持可审查、可回滚？
- 主干是否保持可构建、可测试、可发布？
- 合并前是否有评审、验证结果和影响说明？
- 回滚是否记录原因、范围、版本和验证结果？
