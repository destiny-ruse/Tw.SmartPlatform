# 代码评审规范

## 目标

通过代码评审降低缺陷、回归、安全问题、兼容性破坏和不可维护变更进入主干的风险。

## 适用范围

适用于 pull request、merge request、补丁评审、自动生成代码复核，以及涉及源码、测试、文档、工具、CI 配置、部署配置、数据库迁移和 API 契约的变更。

## 规范要求

- 代码评审必须优先检查正确性、数据安全、权限边界、兼容性、可观测性、回滚风险和缺失测试。
- 阻断性问题必须标记为必须修复，并说明失败场景、破坏的契约或不可接受的运行风险。
- 非阻断性改进意见必须明确为应当处理或可以处理，不得将个人偏好伪装成质量门禁。
- 每条评审意见必须定位到具体文件、行号、配置项、接口或测试场景，并给出可执行修正方向或需要回答的问题。
- 评审必须识别新增、修改或删除行为对应的测试缺口。
- 合并前必须确认阻断性意见已修复，或已按例外流程记录风险。
- 评审者不得要求提交者重写与本次风险无关的大范围代码。
- 自动生成或批量生成代码必须说明已检查范围和未覆盖风险。

## 评审职责

提交者必须提供变更背景、范围、风险、验证方式和必要的回滚影响。

评审者必须判断业务行为、模块边界、测试覆盖、安全风险、性能影响、可观测性、兼容性和文档影响。

Tech Lead 必须对高风险变更、跨模块变更和长期技术债引入进行把关。

## 评审范围

评审必须覆盖：

- 需求或缺陷是否被正确解决。
- 边界条件、异常路径和权限边界是否完整。
- 测试是否覆盖核心路径和风险路径。
- 日志、指标或链路追踪是否支持问题定位。
- API、数据库、消息和配置是否存在兼容性影响。
- 发布、回滚、数据迁移和运行环境是否受到影响。

## 落地要求

- 大变更必须拆分到可评审范围。
- 风格问题应当由格式化、Lint 或静态检查处理。
- 人工验证必须记录步骤、环境、结果和剩余风险。
- 评审争议必须围绕事实、风险和规范要求处理，不得以个人偏好替代工程判断。

## 检查清单

- 是否先检查正确性、安全、兼容性、回归风险和缺失测试？
- 阻断性意见是否说明失败场景、影响范围和修正方向？
- 风格偏好是否与必须修复问题明确区分？
- 新增或修改行为是否有自动化测试或人工验证记录？
- 契约、文档、迁移、CI 或生成文件是否同步更新？
- 未解决风险是否形成例外记录？
