# 仓库组织规范

## 目标

统一仓库边界、目录职责、仓库内容、所有权和归档迁移要求，保证代码资产可追踪、可评审、可构建、可交接。

## 适用范围

适用于应用代码仓库、公共组件仓库、规范仓库、工具脚本仓库、基础设施仓库和自动化配置仓库。

## 规范要求

- 每个仓库必须指定负责人或负责团队。
- 仓库必须包含用途说明、运行方式、构建方式、测试方式、发布方式和负责人信息。
- 源码、测试、构建脚本、部署描述、配置模板和项目文档必须纳入版本管理。
- 仓库目录必须区分源码、测试、文档、工具、配置、部署资产和生成产物。
- 不得提交密钥、生产数据、个人环境文件、本地 IDE 状态、临时文件和无法复现的生成产物。
- 新增顶层目录必须有明确职责，并在 README 或相邻说明中提供入口。
- 生成索引、缓存和工具输出不得与正式规范资料、源码或手写文档混放。

## 仓库边界

仓库边界应当与系统职责、团队所有权和发布节奏保持一致。一个仓库不应同时承载多个生命周期完全不同的系统。

拆分仓库必须具备明确原因，例如独立发布、独立回滚、权限隔离、团队所有权差异或公共组件复用。

## 仓库内容

仓库应当包含：

- 生产源码。
- 自动化测试。
- 构建脚本和工具入口。
- 部署描述或运行说明。
- 配置模板。
- 项目文档。
- 发布、回滚或迁移说明。

仓库不得包含：

- 密钥、令牌、证书私钥和个人凭据。
- 未脱敏生产数据和生产日志。
- 本地缓存、临时目录和个人 IDE 状态。
- 无法由源码和工具重复生成的大型二进制产物。

## 所有权

仓库负责人必须维护仓库说明、评审规则、发布边界、归档状态和风险例外。

公共仓库必须说明使用边界、兼容性策略和支持方式。无人维护的公共仓库必须完成移交、归档或明确禁止使用。

## 落地要求

- 代码评审必须检查新增目录、生成产物、配置文件和敏感信息风险。
- 仓库迁移必须保留提交历史、发布记录、问题追踪记录或迁移说明。
- 仓库归档前必须确认生产依赖、制品依赖、配置依赖和文档引用已处理。

## 检查清单

- 仓库是否有明确负责人或负责团队？
- README 是否说明用途、运行、构建、测试、发布和负责人？
- 源码、测试、脚本、部署、配置和文档是否边界清晰？
- 是否排除了密钥、生产数据、临时文件和个人环境文件？
- 生成产物是否可追溯到源文件和生成命令？
- 仓库迁移或归档是否保留必要追踪信息？
