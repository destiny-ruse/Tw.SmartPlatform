# API 设计规范

## 目标

统一成都天问互联 API 的资源建模、协议语义、响应结构、错误表达、版本兼容、幂等性和契约治理要求，降低前后端协作、移动端接入、跨服务调用和系统集成中的兼容性风险。

## 适用范围

适用于 HTTP JSON API、REST API、gRPC 服务、AsyncAPI 消息契约、网关路由、OpenAPI 契约、接口 Mock、SDK 生成和跨团队接口评审。

## 规范要求

- REST API 路径必须表达稳定业务资源，使用名词复数和稳定标识符，不得使用 `getOrder`、`doCreate` 等动词式 RPC 路径。
- HTTP 方法必须遵守语义：`GET` 只读，`POST` 创建资源或触发非幂等动作，`PUT` 整体替换，`PATCH` 局部更新，`DELETE` 删除、撤销或关闭资源。
- HTTP 状态码必须与操作结果一致。客户端输入错误使用 4xx，服务端不可预期失败使用 5xx，异步受理可以使用 `202 Accepted`。
- 请求体、查询参数、路径参数和请求头必须在信任边界入口完成输入校验，不得依赖前端校验或数据库约束作为唯一校验手段。
- API 响应必须使用统一响应结构，不得暴露内部实体、数据库字段名、临时调试字段或未脱敏信息。
- 错误响应必须包含稳定错误码、可理解错误信息、请求关联标识和必要错误上下文。
- 删除字段、改变字段类型、改变枚举含义、改变分页语义、改变错误码属于破坏性变更，必须提供新版本或迁移策略。
- 可重试写操作必须具备幂等语义；非幂等写操作必须明确不支持重复提交，并向调用方说明处理方式。
- gRPC proto 必须保持字段编号稳定，不得复用已删除字段编号。
- AsyncAPI 消息契约必须定义主题、消息名称、消息键、Schema、兼容规则、重试语义和消费方责任。

## REST API

资源路径应当使用业务资源名称，例如 `/api/v1/orders/{orderId}`。资源名称不得直接暴露数据库表名、内部类名或方法名。嵌套资源不应超过两级；复杂查询应当使用查询参数或明确的搜索资源。

分页、排序和过滤字段必须在接口契约中说明。分页响应必须区分空集合和缺失字段，并提供可判断结果范围或下一页条件的信息。

API 版本必须在路径或协商机制中可发现。同一 API 集合必须使用一致的版本策略，不得让客户端通过部署环境、网关规则或隐藏配置推断版本。

## 数据格式

公开契约中的 JSON 字段名必须使用稳定 `camelCase`，Proto 字段使用 `snake_case`。同一契约内不得混用多种字段命名风格。

日期时间必须使用包含时区语义的 ISO 8601 字符串或明确的日期时间约定。金额必须使用十进制字符串或明确精度的整数最小单位，并同时声明币种。枚举必须使用稳定英文标识值，新增值必须保持消费者兼容。ID、分页游标、Token 和外部引用值必须作为不透明字符串处理。

可选字段、空集合、字段省略和显式错误必须在契约中说明。不得要求客户端解析 ID 结构、数据库自增序号含义或内部分页状态。

## 响应结构

响应结构必须稳定。业务成功、业务失败和系统异常不得混用同一种模糊结构。服务内部对象不得直接作为外部响应模型，接口模型必须与领域模型、存储模型保持边界。

列表响应必须明确数据集合、分页信息和结果范围。字段是否允许为空必须在契约中声明。新增字段应当保持向前兼容，调用方不得依赖未知字段缺失或固定字段顺序。

## 错误响应

错误码必须稳定、可检索、可定位。错误信息应当面向调用方说明处理方向，不得暴露堆栈、SQL、密钥、令牌、内部地址、原始敏感载荷和第三方未脱敏错误。

错误响应应当包含请求关联标识，便于通过日志、指标和链路追踪定位。业务拒绝、输入校验失败、权限失败、资源不存在、并发冲突、依赖失败和未知异常必须有清晰分类。

## 幂等与重试

声明可重试的写操作必须定义幂等键来源、幂等窗口、重复请求响应、冲突处理和审计记录。不得在未定义幂等语义的情况下要求调用方重试写操作。

`GET` 必须只读，不得产生业务副作用。`PUT` 和具备明确资源标识的 `DELETE` 应当具备幂等语义。对账、支付、库存、扣费、发券、通知等关键写操作必须在接口设计阶段明确重复提交处理方式。

## gRPC 与 AsyncAPI

gRPC 服务、方法和消息命名必须表达业务语义。字段编号必须长期稳定；删除字段必须保留编号占位，不得复用。枚举值必须保留兼容空间，并定义未知值处理方式。

AsyncAPI 消息契约必须说明生产者、消费者、消息兼容性、重试策略、死信处理、幂等键和消费确认边界。消息 Schema 变更不得破坏既有消费者。

## 落地要求

- API 设计必须在开发前明确资源、方法、状态码、响应结构、错误码、版本策略和输入校验规则。
- 接口变更必须识别兼容性影响，并在评审中说明是否影响前端、移动端、外部调用方、SDK 或消息消费者。
- 关键 API 必须具备契约测试、接口 Mock 或等效验证方式。
- 消息契约必须纳入接口评审，不得只通过口头约定完成生产者和消费者对齐。
- 破坏性变更必须具备迁移窗口、兼容策略和回退处理。

## 检查清单

- API 路径是否表达稳定业务资源？
- HTTP 方法、状态码、幂等性和重试行为是否一致？
- 输入是否在信任边界入口完成校验？
- 响应结构和错误响应是否稳定、可理解、可追踪？
- 数据格式是否在 JSON、Proto、数据库和客户端类型之间保持一致？
- 破坏性变更是否有新版本、迁移策略和回退处理？
- gRPC 字段编号和 AsyncAPI 消息契约是否保持兼容？
- 关键接口是否具备契约测试、Mock 或等效验证？
