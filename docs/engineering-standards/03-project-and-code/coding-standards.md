# 通用编码规范

## 目标

定义跨语言通用编码要求，提升代码可读性、可维护性、可测试性、安全性和运行可诊断性，使不同技术栈团队能够基于同一质量语言进行开发、评审和交接。

## 适用范围

适用于 .NET Core、Java、Python、Vue、uni-app、TypeScript、JavaScript 项目中的源码、测试、配置、脚本、接口模型、数据模型和公共组件。语言专项规范只补充语言差异，不替代本文件要求。

## 规范要求

- 命名必须表达领域含义、职责、生命周期或工程用途，不得使用无法独立判断含义的名称。
- 同一概念在同一边界内必须使用同一词汇，不得用多个名称表达同一业务对象。
- 函数、类、模块和组件必须职责清晰，不得在一个单元内混合无关职责。
- 公共 API、共享库入口、跨模块接口和关键配置必须具备文档注释或等价契约说明，覆盖行为、输入、输出、错误语义和副作用。
- 错误处理必须保留诊断上下文，并避免向调用方、日志和响应泄露敏感信息。
- 日志必须支持问题定位、审计和运行观测，不得只输出不可查询的自由文本。
- 配置必须按环境外部化，不得在源码中硬编码环境地址、密钥、账号、开关和生产参数。
- 用户可见文案必须满足国际化和可维护要求，不得散落在业务逻辑中。
- 格式化、静态检查和基础质量检查应当由工具统一执行。

## 命名

名称应当让读者直接判断业务对象、职责、状态或用途。禁止使用 `data`、`info`、`obj`、`tmp`、`common`、`manager`、`handle`、`doWork` 等无法表达真实意图的名称。

布尔值必须表达判断语义，可以使用 `is`、`has`、`can`、`should`、`enabled` 等稳定结构。集合、映射和计数名称必须表达元素类型或键值含义，例如 `orders`、`ordersByCustomerId`、`retryCount`。

外部协议、第三方接口和生成代码中的固定名称可以在边界层保留，但进入领域模型、业务服务或公共接口时应当转换为本项目一致的命名。

## 函数、模块与组件

函数应当只完成一项清晰职责，并暴露明确的输入、输出和失败行为。复杂流程应当拆分为可理解、可测试的小单元。

模块边界必须满足以下要求：

- 对外职责清晰。
- 内部实现可以替换而不破坏调用方。
- 不通过全局可变状态、隐式上下文或隐藏副作用完成协作。
- 不把外部系统细节扩散到核心业务逻辑。
- 跨模块依赖通过明确接口、服务、适配器或事件表达。

## 注释与说明

注释用于补充代码无法直接表达的意图、约束、风险和契约。注释不得复述语法动作，不得替代清晰命名、合理拆分和明确类型。

所有注释中的自然语言必须使用简体中文。代码标识符、协议名、标准缩写、第三方字段和外部契约原文可以保留英文。

注释文本、参数描述、返回值描述、异常说明和单行注释末尾不使用中英文句号。属性、字段、组件属性和访问器注释必须直接描述成员含义，不得包含“获取”“设置”“获取或设置”等模板化字样。

文档注释必须解释被注释对象的具体职责、输入含义、返回语义、失败语义、约束或副作用，不得只复述标识符、语法动作或声明类型。

文档注释不得使用“执行 X 操作”“验证 X 场景”“验证 X 相关行为”“X 参数”“X 的执行结果”“表示 X 声明”“表示 X 字段”“表示 X 属性”“表示 X 常量”“表示 X 类型”“定义 X 契约”“根据当前契约完成 X 处理流程”“当前调用传入的 X 值”“当前对象暴露的 X 配置值”“X 在当前模型中的语义”“处理 X 对应的业务逻辑”“用于指定 X”“解析或生成后的文本值”“当前流程完成后产生的返回值”“当前成员”等模板化句式。参数、返回值、属性和字段注释不得只由标识符加通用名词组成，必须说明该值在当前契约中的业务或技术含义。

### 文档注释

人工维护的类型、接口、函数、方法、构造函数、属性、字段、组件、事件、配置对象和导出 API 必须具备文档注释或等价契约说明。该规则覆盖 `public`、`internal`、`protected` 和 `private` 可见性。

文档注释必须按适用场景覆盖以下内容：

- 类型、接口、组件或模块的职责。
- 参数、属性、输入对象和配置项含义。
- 返回值、输出对象、事件载荷和状态变化。
- 异常、错误码、错误响应或失败语义。
- 副作用、幂等性、事务边界、外部调用和性能影响。
- 安全、隐私、兼容性、迁移和数据一致性约束。

语言专项规范定义文档注释的具体形式，例如 .NET XML 注释、JavaDoc、Python docstring、TSDoc 或 JSDoc。公共规则与语言专项同时适用。

### 内部注释

方法、函数或组件内部存在以下情况时，必须添加内部注释：

- 复杂算法或复杂业务流程。
- 代码需要解释为什么这样处理，而不是只说明做了什么。
- 兼容旧客户端、旧数据、旧协议或外部系统缺陷。
- 规避已知缺陷、临时方案、技术债或 Hack。
- 非显而易见的条件分支、边界处理、并发控制或性能取舍。

内部注释优先使用单行注释。单行注释应位于被说明代码上方并与代码对齐，注释与代码之间不留空行，注释上方保留空行；代码块第一行可以不保留空行。单行注释标记和文本之间必须保留一个空格。

```csharp
// 旧客户端不发送 Accept 头时，默认回退到 JSON
if (string.IsNullOrEmpty(acceptHeader))
{
    // ...
}
```

注释必须随代码同步维护。发现注释与实现冲突时，必须更新或删除注释。TODO、FIXME、HACK 必须说明原因、边界和可追踪事项，不得留下无责任上下文的永久待办。

## 错误处理

错误处理必须让调用方能够判断失败类型，让维护人员能够定位问题，让系统能够执行正确的重试、补偿或降级策略。

错误处理必须满足以下要求：

- 区分输入校验错误、认证授权错误、领域规则错误、资源不存在、并发冲突、下游依赖错误和系统未知错误。
- 面向调用方的错误必须映射为稳定错误码、协议状态和安全消息。
- 未知异常必须在边界层统一捕获、记录并转换为通用系统错误。
- 可重试错误和不可重试错误必须明确分类。
- 不得吞掉异常后继续返回成功。
- 不得直接返回异常类名、堆栈、SQL、密钥、令牌、证件号、手机号或原始敏感载荷。

仓库自有代码显式抛出的异常应当使用简体中文消息。参数名、错误码、协议字段、算法名和第三方原文可以保留英文。

## 日志

日志必须服务于排障、审计和运行观测。生产日志应当使用结构化格式，并包含服务、环境、版本、请求关联标识、业务标识、事件含义和失败原因等可查询字段。

日志级别必须表达影响：

- `ERROR` 用于请求失败或需要处置的系统错误。
- `WARN` 用于降级、重试耗尽或可恢复异常。
- `INFO` 用于关键状态变化。
- `DEBUG` 用于非生产诊断。

日志不得记录密钥、令牌、完整证件号、完整手机号、密码、原始敏感载荷和可反推敏感信息的片段。高频路径必须控制日志级别、采样和聚合，避免影响性能和成本。

## 配置

配置必须具备清晰来源、覆盖顺序、默认行为和校验规则。配置键应当按功能域分组并使用稳定名称，不得在业务逻辑中散落字符串 key 或以环境名拼接配置路径。

配置项应当说明名称、用途、类型、默认值或缺省行为、是否必填、是否敏感、生效范围和变更影响。生产环境缺失必填配置时，应用必须启动失败。

密钥、令牌、证书和连接串必须来自受控密钥来源，例如密钥管理服务、部署平台安全变量或受控配置中心，不得写入仓库配置、示例日志、默认值和测试样例。

## 国际化

用户可见文本应当通过统一资源文件或文案管理方式维护。多语言产品的按钮、标题、通知、错误提示、表单 label、placeholder、辅助说明、路由标题、ARIA 名称和图标按钮说明必须纳入国际化处理。

语言键必须稳定、可搜索，并按领域或页面组织。占位符必须使用具名参数，并在所有语言包中保持同名、同语义和同格式。不得通过拼接半句生成完整自然语言句子。

日期、时间、数字、货币、单位和复数表达必须保留本地化处理空间。缺失翻译必须有可验证的回退策略，不得静默显示 key 或空字符串给用户。

## 检查清单

- 命名是否能表达领域含义、职责、生命周期或工程用途？
- 同一概念是否在代码、测试、配置、文档和部署资产中保持词汇一致？
- 函数、模块和组件是否职责清晰、输入输出明确？
- 公共接口是否具备文档注释或等价契约说明？
- 注释是否使用简体中文，并解释原因、约束、风险或契约？
- 参数、返回值、异常、属性和单行注释是否符合文本格式要求？
- 错误处理是否保留诊断上下文并避免敏感信息泄露？
- 日志是否结构化、可查询、可关联并完成脱敏？
- 配置是否外部化、可校验、可追踪且不包含密钥？
- 用户可见文案是否满足国际化要求？
