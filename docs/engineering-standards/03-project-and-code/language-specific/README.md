# 语言专项规范

## 目标

说明不同技术栈在项目组织、命名、注释、类型系统、构建工具、运行环境和框架边界上的专项要求，保证语言差异不会降低成都天问互联工程规范的统一质量基线。

## 适用范围

适用于 .NET Core、Java、Python、Vue、uni-app、TypeScript、JavaScript 项目，以及混合技术栈项目中的对应模块。

## 使用方式

研发团队阅读语言专项规范时，必须先理解项目结构、通用编码、测试、安全和交付要求，再阅读当前项目对应语言章节。语言专项规范用于补充差异，不得降低通用规范的要求。

阅读顺序如下：

1. 阅读[项目结构规范](../project-structure.md)和[通用编码规范](../coding-standards.md)。
2. 阅读当前项目对应语言专项规范。
3. 对照项目实际目录、构建命令、测试命令和运行环境完成检查。

## 通用前提

- 项目必须记录运行时版本、包管理器、构建命令、测试命令、格式化命令和发布产物。
- 项目必须使用团队认可的格式化、Lint、静态检查、测试和构建方式。
- 项目必须遵守语言生态默认目录和构建约定；确需偏离时，必须在项目说明中解释原因和影响。
- 项目必须按语言生态使用文档注释形式，并遵守通用注释规则。
- 新项目必须启用适合技术栈的静态检查、依赖风险检查和自动化测试。
- 语言生态工具生成的文件必须有清晰边界，不得与人工维护代码混淆。

## 与通用规范的关系

通用规范定义跨语言一致要求，例如命名、注释、错误处理、日志、配置、安全、测试和文档。语言专项规范只描述该技术栈特有要求，例如项目组织、框架边界、包管理、类型系统、构建工具、运行时约束和平台兼容性。

当语言专项规范与通用规范表述存在差异时，必须选择更严格且更能保护系统质量、数据安全和交付稳定性的要求。

## 检查清单

- 项目是否已阅读并执行对应语言专项规范？
- 运行时版本、包管理器和构建方式是否记录清楚？
- 格式化、Lint、测试和构建命令是否可重复执行？
- 语言专项是否只补充差异，没有降低通用规范基线？
- 生成文件、框架约定和人工代码边界是否清晰？
