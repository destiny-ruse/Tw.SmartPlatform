# TypeScript 专项规范

## 目标

统一 TypeScript 项目的类型安全、领域类型、运行时校验、模块边界、命名、公共类型和运行环境约束，避免运行期才暴露字段缺失、空值误用和异步竞态。

## 适用范围

适用于 TypeScript 前端应用、Node.js 服务、共享 SDK、组件库、工具项目和 Vue TypeScript 项目。

## 规范要求

- 项目必须记录 TypeScript 版本、Node.js 版本或浏览器运行环境版本。
- 新项目必须启用 strict type checking。
- API 响应、路由参数、组件 props、emits、状态对象和跨模块导出值必须声明明确类型，不得依赖隐式 `any`。
- 共享类型必须表达领域契约，不得只复制偶然的接口传输形状。
- 外部输入必须保留运行时校验，包括 HTTP 响应、URL 参数、本地存储、消息数据、浏览器 API 和第三方 SDK 返回值。
- `null`、`undefined`、空数组和空字符串必须有一致语义；可选字段进入视图或业务逻辑前必须完成默认值、保护分支或显式窄化。
- 不得使用非空断言 `!` 绕过真实空值风险；只有生命周期或测试夹具已证明值存在时才可以使用，并必须有就近说明。
- `any` 必须限制在清晰边界内；确需使用时，必须说明原因并尽快窄化。
- 模块边界必须区分 UI、API client、领域逻辑、状态管理和工具函数。
- 公共类型和导出 API 必须提供 TSDoc、JSDoc、示例或等价契约说明，并遵守通用注释规则。

## 类型建模

类型必须表达业务语义。后端响应、数据库字段或第三方对象不得原样扩散为领域模型。传输层类型、领域类型和视图类型应当保持边界，并在请求层、adapter 或 composable 中完成转换。

泛型、联合类型和类型守卫必须表达真实约束，不得为了消除报错写过宽的 `Record<string, unknown>` 或类型断言。类型断言 `as` 必须靠近可信边界，并通过校验、解析或测试证明来源。

测试数据必须满足同一类型契约，可以使用 builder 或 fixture，不得用不完整对象强制断言通过编译。

## 异步与模块边界

异步 API 调用必须表达 loading、成功、失败、取消和重试状态。不得让未处理 Promise 进入组件渲染路径或服务边界。

模块不得跨越所有权边界直接读取其他功能目录的内部文件。共享类型、工具和服务必须通过该模块公开出口导出。

浏览器和 Node.js runtime assumptions 必须明确。涉及 `fetch`、Web Crypto、文件系统、WebSocket、Worker、Timer 和全局对象时，必须说明运行环境和兼容范围。

## TSDoc 与 JSDoc

公共类型、接口、函数、类、组合式函数、SDK 方法和跨包导出值必须使用 TSDoc、JSDoc 或相邻文档说明契约。

文档注释必须按适用场景使用 `@param`、`@returns`、`@throws`、`@example`、`@template` 等标签说明参数、返回值、异常语义、示例和泛型含义。存在外部调用、运行时校验、缓存、副作用、取消或重试行为时，必须在说明中表达。

```typescript
/**
 * 查询指定订单详情
 *
 * @param orderId 订单标识
 * @returns 订单详情
 * @throws 查询失败或订单不存在时抛出业务错误
 */
export async function getOrderDetail(orderId: string): Promise<OrderDetail>
```

## 常见反模式

- 为了绕过编译错误大量使用 `any`。
- 把接口响应类型直接当作领域模型长期使用。
- 只依赖 TypeScript 类型检查，不校验外部输入。
- 类型定义散落在调用方，导致同一概念有多个版本。
- 浏览器或 Node.js 运行时假设没有记录。
- 使用非空断言掩盖真实空值路径。
- 公共导出 API 缺少 TSDoc 或 JSDoc。

## 检查清单

- 新项目是否启用 strict type checking？
- TypeScript 和运行环境版本是否记录？
- 共享类型是否表达领域契约？
- `any`、`as` 和非空断言是否被限制在清晰边界内？
- 外部输入是否有运行时校验？
- 传输层、领域层和视图层类型是否保持边界？
- 公共类型和导出 API 是否具备 TSDoc、JSDoc 或等价契约说明？
- 浏览器和 Node.js runtime assumptions 是否明确？
