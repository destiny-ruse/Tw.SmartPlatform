# JavaScript 专项规范

## 目标

统一 JavaScript 项目的运行时版本、模块边界、Lint、格式化、包管理、输入校验和兼容性要求，降低缺少静态类型带来的运行期风险。

## 适用范围

适用于 JavaScript 前端应用、Node.js 服务、脚本工具、公共组件和遗留项目维护。

## 规范要求

- 项目必须记录 Node.js 版本或浏览器兼容范围。
- 项目必须记录包管理器、锁定文件策略、构建命令、测试命令和运行入口。
- 项目必须使用一致的 linting 和 formatting 规则。
- 项目必须避免 implicit globals 和共享全局状态修改。
- 外部输入必须进行显式运行时校验，包括 HTTP 响应、URL 参数、本地存储、消息数据、文件输入和第三方 SDK 返回值。
- 模块边界必须区分 UI、API client、领域逻辑、状态管理和工具函数。
- 长期维护的 JavaScript 项目应当逐步引入 JSDoc、类型声明或 TypeScript 迁移边界。
- 公共函数、类、模块出口和脚本入口必须提供 JSDoc 或等价契约说明，并遵守通用注释规则。
- 浏览器项目必须明确兼容范围、polyfill、转译目标和构建产物要求。

## 模块与运行时

JavaScript 项目缺少编译期类型保障，因此必须通过清晰模块边界、运行时校验、自动化测试和代码审查控制风险。

Node.js 服务必须固定运行时版本，并通过锁定文件保证依赖可重复安装。脚本项目必须记录执行环境、参数、外部依赖和副作用。

浏览器项目不得默认依赖最新浏览器能力。使用新的浏览器 API、CSS 特性、WebView 能力或设备能力前，必须确认支持范围并提供降级策略。

## 全局状态与输入校验

不得未声明变量，不得通过修改内置对象、全局对象或共享单例传递业务状态。确需使用全局配置时，必须有明确命名空间、初始化顺序和只读边界。

外部输入进入业务逻辑前必须校验结构、类型、范围和空值语义。不得把不可信对象直接传入核心流程。

## JSDoc 文档注释

公共函数、类、模块出口、Node.js 服务入口、脚本入口和共享工具必须使用 JSDoc 或相邻文档说明契约。

JSDoc 必须按适用场景使用 `@param`、`@returns`、`@throws`、`@example` 和 `@template` 说明参数、返回值、异常语义、示例和泛型含义。涉及异步、外部调用、全局状态、文件系统、网络请求或副作用时，必须说明影响边界。

```javascript
/**
 * 读取并解析本地配置文件
 *
 * @param {string} filePath 配置文件路径
 * @returns {Promise<object>} 配置对象
 * @throws 文件不存在或解析失败时抛出错误
 */
async function loadConfig(filePath) {}
```

## 常见反模式

- 未声明变量导致 implicit globals。
- 在多个模块中修改共享全局对象。
- 没有锁定文件，依赖安装结果不可重复。
- 外部输入直接进入业务逻辑。
- 浏览器兼容范围不清，生产环境才发现兼容问题。
- 以自由对象传递核心业务数据，缺少校验和测试。
- 公共函数缺少 JSDoc，调用方只能阅读实现。

## 检查清单

- Node.js 版本或浏览器兼容范围是否明确？
- 包管理器和锁定文件策略是否记录？
- linting 和 formatting 是否统一？
- 是否避免 implicit globals 和共享全局状态？
- 外部输入是否有显式运行时校验？
- 模块边界是否清楚区分 UI、API client、领域逻辑、状态管理和工具函数？
- 公共函数、模块出口和脚本入口是否具备 JSDoc 或等价契约说明？
- 长期维护项目是否具备类型标注、JSDoc 或迁移边界？
