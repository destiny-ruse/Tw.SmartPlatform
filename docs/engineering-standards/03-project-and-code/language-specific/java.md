# Java 专项规范

## 目标

统一 Java 项目的构建工具、包结构、命名、注释、分层边界、异常语义、依赖管理和质量检查方式，保证 Java 服务、组件和工具具备可维护、可测试、可交付的工程结构。

## 适用范围

适用于 Java 后端服务、批处理任务、公共组件、SDK、内部工具和多模块项目。

## 规范要求

- 单个项目内必须统一使用 Maven 或 Gradle，不得混用多个构建体系。
- 项目必须记录 JDK 版本、构建命令、测试命令、运行方式和制品输出。
- 包名必须使用全小写反向域名或项目约定根包，并按领域或层次分段。
- 类、接口和枚举必须使用 PascalCase，并表达领域对象、能力或职责。
- 方法、字段、局部变量和参数必须使用 camelCase，并表达动作、状态或数据含义。
- 常量必须使用 UPPER_SNAKE_CASE，并只用于真正不可变值，不得把环境配置、可变阈值或数据库数据写成常量。
- 布尔方法和变量应当使用 `is`、`has`、`can`、`should` 等判断语义。
- 接口名称不得强制使用 `I` 前缀，应当直接表达能力；实现类名称必须说明实现差异。
- 公共 API、扩展点和共享组件必须提供 JavaDoc 或等价接口说明，并遵守通用注释规则。
- 构建过程必须执行格式化、静态分析、测试和依赖风险检查。

## 包结构与分层

包结构必须服务业务边界，而不是只按技术层堆叠。大型系统可以按业务上下文或模块组织，再在模块内部划分接口、应用服务、领域模型和基础设施。

controller、service、repository、domain、infrastructure 等职责必须清晰。controller 只负责协议适配和请求响应转换；service 负责应用流程；domain 表达核心业务规则；repository 负责持久化边界；infrastructure 封装外部系统、缓存、消息和文件能力。

跨模块依赖必须通过公开接口或模块出口完成。不得从其他模块直接读取内部实现、测试夹具或私有包。

## 异常与事务

异常设计必须在服务边界处稳定。对外接口必须定义可预期的错误码、异常类型或错误响应，不得把底层数据库、缓存、HTTP 客户端和消息中间件异常直接暴露给调用方。

事务边界必须与业务一致性边界匹配。不得在长事务中执行不可控外部调用。涉及消息、缓存和异步任务时，必须明确提交顺序、补偿方式和失败处理。

依赖版本必须集中管理。多模块项目不得让各模块各自声明不兼容版本。

## JavaDoc 文档注释

公共类、接口、枚举、方法、构造函数和扩展点必须使用 JavaDoc 说明职责和调用契约。JavaDoc 必须与通用注释规则一致。

方法注释必须按适用场景使用 `@param`、`@return`、`@throws` 和 `@param <T>` 说明参数、返回值、异常语义和泛型含义。存在副作用、事务边界、幂等性、外部调用或性能成本时，必须在正文中说明。

```java
/**
 * 扫描指定包路径下的服务类型
 *
 * @param packageName 要扫描的包名
 * @return 发现的服务类型集合
 * @throws IllegalArgumentException packageName 为空时抛出
 */
List<Class<?>> scan(String packageName)
```

## 常见反模式

- `service` 层成为所有业务逻辑、数据库访问和外部调用的堆放处。
- 包名按个人习惯命名，无法反映业务边界。
- 所有异常都捕获后返回通用失败，丢失诊断上下文。
- 多模块项目依赖版本分散，构建结果不可预测。
- 单元测试依赖真实数据库或外部服务。
- 长事务中调用远程服务，导致锁等待和回滚不可控。
- 公共 API 缺少 JavaDoc，调用方只能阅读实现。

## 检查清单

- Maven 或 Gradle 是否统一？
- JDK 版本、构建命令、测试命令和运行方式是否记录？
- 包结构是否反映组织、产品和业务边界？
- 命名是否符合 Java 生态和领域语义？
- controller、service、repository、domain、infrastructure 职责是否清晰？
- 异常语义是否在服务边界处稳定？
- 公共 API 是否具备 JavaDoc 并覆盖参数、返回值和异常语义？
- 依赖版本、格式化、静态分析、测试和依赖检查是否可执行？
