# 项目结构规范

## 目标

统一不同语言项目的目录职责、配置边界、环境隔离、生成产物管理和项目文档要求，使研发、测试、运维和评审人员能够快速识别项目入口、构建方式、测试方式、部署资产和运行依赖。

## 适用范围

适用于 .NET Core、Java、Python、Vue、uni-app、TypeScript、JavaScript 项目，以及包含多种语言的混合仓库、应用仓库、服务仓库、公共组件仓库和工具脚本仓库。

## 规范要求

- 项目必须清晰区分源码、测试、文档、脚本、配置、部署资产、运行资产和生成产物。
- 可运行代码必须位于约定的源码目录，不得隐藏在 `docs/`、`tools/`、`scripts/` 等非源码目录中。
- 测试目录必须能够从路径或命名关联到被测源码，不得把长期维护的测试样例混入生产代码目录且无命名区分。
- 脚本、生成器和校验工具必须提供可从仓库根目录执行的入口，不得依赖个人本地路径。
- 部署资产和运行配置必须位于可识别目录，不得与业务源码混放到无法判断发布边界。
- 生成产物必须位于可识别目录或使用可识别后缀，并说明来源、生成命令和维护边界。
- 新增顶层目录必须具备明确职责，并在项目说明或相邻文档中提供入口。
- 项目不得新增含义不明的 `misc/`、`new/`、`temp/`、`final/` 等正式目录。

## 目录职责

项目可以按语言生态采用自然目录结构，但目录职责必须明确。通用目录约定如下：

```text
project-root/
|-- src/        # 生产源码，或语言生态约定的源码入口
|-- tests/      # 自动化测试，或语言生态约定的测试入口
|-- docs/       # 项目文档、接口说明、运行说明和交接资料
|-- scripts/    # 可重复执行的本地脚本和 CI 辅助脚本
|-- tools/      # 共享工具、生成器、校验器和开发辅助工具
|-- deploy/     # 部署描述、发布模板、Kubernetes 或 Helm 资产
|-- ops/        # 运行手册、告警说明、仪表盘说明和故障处理资料
|-- config/     # 非密钥配置模板和配置说明
`-- README.md   # 项目入口说明
```

语言生态已有强约定时，应当优先遵守生态约定。例如 Java 项目可以使用 `src/main` 与 `src/test`，.NET 项目可以使用解决方案和项目目录，前端项目可以使用 `src/`、`public/` 与构建配置目录。生态约定与企业目录约定不一致时，项目入口文档必须说明实际目录职责。

## 文件落点规则

新增、移动或生成文件前，必须先判断文件性质，再按固定目录落点。不得因为临时分析、调试验证、工具输出或个人习惯，将文件放入仓库根目录、业务源码目录旁边或含义不清的目录。

文件必须按以下矩阵落点：

| 文件类型 | 固定目录 |
| --- | --- |
| Agent 入口文件 | 仓库根目录的 `AGENTS.md`、`CLAUDE.md` |
| 多智能体公共行为规则 | `.rules/common-agent-instructions.md` |
| AI 编码规则加载索引 | `.rules/ai-coding-rules` |
| Agent 技能定义 | `.agents/skills/<skill-name>` |
| Claude 技能镜像或配置 | `.claude/skills/<skill-name>`、`.claude/settings.json` |
| 技能锁定文件 | `skills-lock.json` |
| .NET 工作区级配置 | `backend/dotnet` |
| .NET 后端服务源码 | `backend/dotnet/Services` |
| .NET Aspire 编排项目 | `backend/dotnet/Aspire` |
| .NET 构建辅助项目 | `backend/dotnet/Build` |
| .NET 后端公共构建块源码 | `backend/dotnet/BuildingBlocks/src` |
| 共享包职责与边界声明 | `<package-root>/package-charter.yaml` |
| .NET 后端公共构建块测试 | `backend/dotnet/BuildingBlocks/tests` |
| Java 后端相关文件 | `backend/java` |
| Python 后端相关文件 | `backend/python` |
| 前端应用源码 | `frontend/apps/<app-name>` |
| 前端共享包 | `frontend/packages/<package-name>` |
| Protobuf 契约 | `contracts/protos` |
| OpenAPI、AsyncAPI 和其他 API 契约 | `contracts/apis` |
| 工程规范正文 | `docs/engineering-standards` |
| Agent 设计文档 | `docs/superpowers/specs` |
| Agent 实施计划 | `docs/superpowers/plans` |
| 普通项目文档和交接说明 | `docs/project` |
| 运行手册、排障资料和告警说明 | `docs/ops` |
| CI/CD 配置和流水线说明 | `deploy/ci-cd` |
| Docker Compose 资产 | `deploy/docker-compose` |
| Kubernetes 和 Helm 资产 | `deploy/k8s-helm` |
| 工具、生成器和校验器源码 | `tools/src` |
| 工具测试 | `tools/tests` |
| 非密钥配置模板和配置说明 | `config` |
| 可提交的生成产物 | `generated/<source-name>` |
| 本地索引、缓存和工具状态 | 不提交，例如 `.codegraph/` |
| 临时分析输出、一次性中间文件和草稿 | 不提交，不得保留在仓库目录中 |

仓库根目录只用于入口文件、仓库级配置、锁定文件和顶层说明。业务源码、测试样例、分析报告、临时脚本、生成结果和工具输出不得直接放在仓库根目录。

目录矩阵中已经定义但尚不存在的目录可以创建。无法归类的文件不得落盘，必须先说明文件用途、候选目录、矩阵缺口和建议新增的目录规则。

临时分析输出、一次性中间文件和草稿不得提交，也不得保留在仓库目录中。确需长期保留时，必须转化为正式文档、测试夹具、工具源码或生成产物后再按矩阵落点。

## 配置与环境隔离

配置必须与代码分离。不同环境的差异应当来自配置源、环境变量、部署参数或配置中心，不得通过修改源码、切换注释代码或维护环境专用分支实现。

配置文件和模板必须满足以下要求：

- 本地、测试、预发和生产环境能够清晰区分。
- 配置模板不得包含密钥、令牌、证书、生产连接串和真实个人信息。
- 必填配置必须有用途、类型、默认行为、取值边界和敏感性说明。
- 生产环境缺失必填配置时，应用必须在启动阶段失败并输出不含敏感值的原因。
- 配置覆盖顺序必须可预测，不得让同一配置项在多个位置产生不可判断的最终值。

## 文档约定

每个项目必须提供项目入口说明，至少包含以下内容：

- 项目用途、系统边界和负责人或负责团队。
- 本地启动方式、依赖服务和必要前置条件。
- 构建、测试、静态检查和格式化命令。
- 配置项来源、必填项和密钥注入方式。
- 数据库、缓存、消息、对象存储、第三方服务等外部依赖。
- 发布、回滚、运行检查和排障入口。
- 公共组件的使用边界、兼容性策略和示例。

公共组件、SDK、框架库和跨团队工具的适用范围、不适用范围、依赖边界、兼容性承诺和迁移指针，必须在该包根目录的 `package-charter.yaml` 中声明。

## 生成产物与脚本

生成代码、契约文件、客户端 SDK、数据库模型、接口类型和静态索引必须能追溯到源文件和生成命令。可提交的生成产物必须位于 `generated/<source-name>`，并说明来源、生成命令和维护边界。工具声明为 generated 的文件不得手工维护；确需人工补充时，必须调整生成源或生成流程。

不可复现的工具输出、扫描缓存、本地索引和一次性分析结果不得作为生成产物提交。

脚本必须说明用途、参数、依赖、执行环境、幂等性和风险。涉及生产数据、发布、回滚、数据库迁移、数据修复和批量任务的脚本必须提供执行边界、停止条件和验证方式。

## 常见反模式

- 源码、脚本、临时文件、测试样例和构建输出混放在同一目录。
- 项目只有代码，没有运行、构建、测试、配置和发布说明。
- 通过修改源码或注释代码切换环境。
- 生成代码无来源说明，无法重复生成。
- 一次性脚本长期保留在正式源码目录。
- 部署文件、运行手册和实际发布流程不一致。

## 检查清单

- 源码、测试、文档、脚本、配置、部署资产和生成产物是否边界清晰？
- 测试路径是否能够关联到被测源码或模块？
- 工具脚本是否能从仓库根目录重复执行？
- 配置模板是否排除了密钥、生产数据和个人本地状态？
- 环境差异是否由配置源控制，而不是由源码分支控制？
- 生成产物是否可识别、可追溯、可重复生成？
- 新增文件是否已按文件落点矩阵放入固定目录？
- 临时输出、本地索引、缓存和工具状态是否排除在提交之外？
- 无法归类的文件是否先补充目录规则，而不是直接落盘？
- 项目入口文档是否覆盖运行、构建、测试、配置、发布和排障？
