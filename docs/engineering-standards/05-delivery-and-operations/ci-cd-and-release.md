# CI/CD 与发布规范

## 目标

统一平台无关的 CI/CD 流水线、质量门禁、环境晋级、版本号、发布策略和回滚策略，降低交付风险并提升发布可追溯性。

## 适用范围

适用于所有需要构建、测试、打包、制品归档、部署、发布或回滚的软件项目。

## 规范要求

- 发布版本必须能够追溯到源码提交、构建任务、测试结果、制品信息和发布留痕。
- 流水线必须覆盖依赖恢复、静态检查、自动化测试、构建、打包、扫描、制品发布、部署和通知等必要阶段。
- 质量门禁必须与项目风险匹配，至少覆盖构建成功、核心测试通过、关键扫描通过和制品生成成功。
- 发布前必须说明范围、风险、验证方式、负责人、回滚方式和沟通渠道。
- 关键系统必须具备可执行的回滚策略。
- 同一发布流程必须优先晋级同一个制品，不得为每个环境重新构建不同制品。
- 生产发布必须识别配置、数据库迁移、依赖系统、缓存、消息和运行资源影响。
- 关键系统应当使用分批、灰度、蓝绿或金丝雀发布策略降低生产风险。

## 流水线阶段

平台无关的流水线通常包含以下阶段：

1. checkout：获取源码。
2. dependency restore：恢复依赖。
3. static checks：格式化、Lint、静态分析和基础质量检查。
4. tests：执行单元测试、集成测试、契约测试或端到端测试。
5. build：编译或构建。
6. package：生成可部署制品。
7. scan：执行安全、依赖、镜像或许可证检查。
8. publish：发布制品到制品库。
9. deploy：部署到目标环境。
10. verification：执行部署后验证。
11. notification：通知相关人员和系统。

不同项目可以根据风险和技术栈裁剪阶段，但裁剪原因必须清楚。影响生产发布的阶段不得绕过质量门禁。

## 质量门禁

质量门禁必须自动化或具备明确人工确认责任。以下情况不得进入生产发布：

- 构建失败。
- 核心自动化测试失败。
- 关键安全扫描、依赖漏洞或许可证检查存在阻断风险。
- 制品无法追溯到源码提交。
- 数据库迁移无回滚或补偿策略。
- 发布范围、验证方式和回滚方式不明确。

门禁例外必须记录原因、风险、负责人、缓解措施、确认人和有效期。例外不得成为长期绕过质量控制的方式。

## 环境晋级

环境晋级必须遵循从低风险环境到高风险环境逐级推进的原则。常见环境包括本地、开发、测试、预发和生产。

同一个制品必须在环境间晋级。环境差异应来自配置、密钥、资源规格和外部依赖地址，不得通过重新构建不同代码或不同制品表达。

生产发布前必须确认制品来源清晰、必要测试已完成、配置已复核、数据迁移影响明确、回滚方式可执行、监控和告警已准备。

## 版本号与发布策略

版本号必须能够关联源码提交和制品信息。团队可以采用语义化版本、日期版本、构建号或内部版本规则，但同一项目必须保持一致。

发布策略必须根据系统风险选择。低风险内部系统可以使用常规发布；用户范围较大或影响面较广的系统应当采用分批发布；需要控制流量或用户范围的系统应当采用灰度、蓝绿或金丝雀发布。

发布计划必须识别发布范围、依赖系统、数据变更、配置变更、用户影响、验证方式、回滚方式、负责人和沟通渠道。

## 回滚策略

回滚策略必须在发布前准备。回滚策略必须说明触发条件、回滚步骤、依赖系统影响、数据变更处理、验证方式和通知对象。

关键系统的回滚必须经过测试或演练。涉及数据库迁移、消息消费、缓存结构或外部系统状态的发布，必须说明前向修复、回滚或补偿策略。

发布失败后必须保留失败原因、处置过程、影响范围、恢复结果和改进事项，以便审计、复盘和持续改进。

## 常见反模式

- 不同环境重新构建不同制品，导致测试结果无法代表生产发布。
- 发布前没有回滚策略。
- 版本号无法关联源码和制品。
- 发布计划只描述步骤，不描述风险和验证方式。
- 质量门禁长期被人工绕过。
- 把具体平台脚本当作唯一规范，导致平台迁移困难。

## 检查清单

- 版本是否能追溯到源码、构建、测试和制品？
- 流水线是否覆盖必要检查、测试、构建、打包、扫描、发布和通知？
- 质量门禁是否覆盖本项目关键风险？
- 是否使用同一制品进行环境晋级？
- 发布计划是否说明范围、风险、负责人、验证方式和沟通渠道？
- 回滚策略是否可执行并经过验证或演练？
