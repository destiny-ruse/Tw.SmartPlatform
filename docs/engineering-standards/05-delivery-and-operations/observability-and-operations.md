# 可观测性与运维协作规范

## 目标

统一结构化日志、指标、链路追踪、告警、运行手册和故障复盘要求，使系统上线后能够诊断、运营、恢复和持续改进。

## 适用范围

适用于生产或准生产运行的软件系统，包括后端服务、前端应用、移动端应用、批处理任务、定时任务、消息消费者和平台组件。

## 规范要求

- 影响用户或业务的失败必须能够通过日志、指标或链路追踪定位。
- 生产日志必须使用结构化日志，并包含服务、环境、版本、关联标识、事件名称和必要业务上下文。
- 关键系统必须覆盖可用性、延迟、吞吐、错误率、资源使用和关键业务计数指标。
- 分布式系统必须传播 request id、trace id、correlation id 或等价关联标识。
- 关键告警必须指定负责人、严重级别、触发条件、用户影响、首个响应动作和升级路径。
- 关键系统必须提供运行手册。
- 重大故障必须进行复盘，并跟踪改进行动直至关闭。

## 结构化日志

日志必须帮助定位问题，而不是只记录“发生错误”。关键日志必须包含事件名称、关联标识、允许记录的业务标识、状态变化、失败阶段、错误原因和耗时。

日志级别必须表达影响。正常业务拒绝不得记录为系统错误。日志不得包含密钥、令牌、完整证件号、完整手机号、密码、原始敏感载荷和可反推敏感信息的片段。

高频日志必须控制级别、采样和保留周期，避免影响性能、成本和排障有效性。

## 指标

指标必须覆盖系统状态和业务状态。系统指标包括可用性、延迟、吞吐、错误率、CPU、内存、磁盘、网络、连接池、队列长度和缓存命中率。业务指标包括订单数、支付成功率、审批积压量、任务成功率和关键流程转化率。

指标命名和标签必须稳定。标签不得使用高基数字段，例如完整用户 ID、手机号、订单号和请求体片段。

关键 SLO 必须能够从指标中计算或验证，告警阈值必须与用户影响和业务风险关联。

## 链路追踪

HTTP、gRPC、消息队列、定时任务、异步任务、外部回调和批处理任务必须尽量保留追踪上下文。

链路追踪必须能够回答请求经过哪些服务、每个阶段耗时多少、失败发生在哪个边界、外部依赖是否异常、重试和降级是否发生。

新增跨服务调用时，必须确认关联标识传递、日志字段、指标和追踪跨度是否完整。

## 告警

告警必须可行动。每个关键告警必须定义负责人、严重级别、触发条件、用户影响、首个响应动作、升级路径、关联仪表盘和运行手册入口。

告警不得只因为技术指标波动而触发，必须结合用户影响、业务风险和持续时间。长期无人处理的告警必须下线、调优或重新分配负责人。

告警恢复条件必须明确。自动恢复不得掩盖持续存在的数据错误、消息积压或降级状态。

## 运行手册

运行手册必须覆盖服务目的、依赖系统、启停方式、关键配置、仪表盘、日志入口、常见故障、排障步骤、回滚方式和升级路径。

运行手册必须跟随系统变化更新。发布、配置、告警、依赖和回滚方式变化时，运行手册必须同步调整。

## 故障复盘

故障复盘必须关注事实、影响、根因和改进。复盘必须包含时间线、用户和业务影响、检测方式、直接原因、根因、处置过程、有效措施、待改进项、行动负责人和完成日期。

重复发生的问题必须升级为治理事项。复盘行动不得只停留在会议结论，必须能够追踪到关闭状态。

## 常见反模式

- 日志只有错误堆栈，没有业务上下文。
- 告警很多但无人响应。
- 指标只覆盖服务器资源，不覆盖业务影响。
- 分布式调用没有关联标识，跨服务排障困难。
- 运行手册上线后不维护。
- 故障复盘只找个人责任，不跟踪改进行动。

## 检查清单

- 用户影响问题是否能通过日志、指标或链路追踪定位？
- 是否传播 request id、trace id 或 correlation id？
- 指标是否覆盖可用性、延迟、吞吐、错误率、资源和业务计数？
- 告警是否有负责人、级别、触发条件、影响和首个响应动作？
- 运行手册是否覆盖依赖、仪表盘、常见故障、回滚和升级路径？
- 故障复盘是否记录时间线、影响、根因、行动和负责人？
