# 运行环境与基础设施规范

## 目标

统一运行环境、配置管理、容器镜像和 Kubernetes 资源命名要求，保证应用运行边界清晰、配置来源可靠、制品可追溯、基础设施资源可治理。

## 适用范围

适用于应用运行环境、环境变量、配置文件、配置中心、容器镜像、镜像仓库、Kubernetes Deployment、Service、ConfigMap、Secret、Ingress、Job、CronJob 和相关运行资源。

## 规范要求

- 环境必须明确区分本地、开发、测试、预发和生产，不得通过修改源码切换环境。
- 配置必须与代码分离。非密钥配置可以进入配置文件或配置中心，密钥必须通过受控密钥来源注入。
- 应用不得在启动日志、错误响应、监控标签、镜像层或配置摘要中输出密钥。
- 容器镜像必须能够追溯到源码版本、构建时间、构建命令和制品版本。
- 容器镜像必须最小化，不得包含无关构建工具、临时文件、密钥、缓存或个人环境配置。
- 生产容器必须使用非 root 用户运行，文件权限必须满足最小权限原则。
- 容器镜像必须进行漏洞扫描，并对高风险漏洞制定处理措施。
- Kubernetes 资源命名必须表达系统、环境、组件和用途，不得使用 `test`、`new`、`tmp` 等含义不清名称。
- Kubernetes 标签必须支持应用识别、环境区分、版本追踪、团队归属和运维查询。
- ConfigMap 和 Secret 必须职责清晰，不得将密钥放入 ConfigMap。

## 环境策略

环境差异必须由配置源表达。不同环境的数据库、缓存、消息、第三方服务和开关配置必须可识别、可审计、可回滚。

生产环境配置变更必须经过复核。影响业务行为的配置变更必须纳入发布计划或运维留痕，确保可追溯。

环境隔离必须覆盖网络、数据、密钥、权限、日志、指标和告警。测试环境不得直接连接生产数据库、生产消息主题或生产第三方账号。

## 配置管理

配置项必须说明名称、用途、是否必填、默认行为、是否敏感、适用环境和变更影响。

应用启动时必须检查必要配置是否存在，但不得在日志中输出完整敏感值。配置覆盖顺序必须可预测，避免同一配置项在多个来源产生不可判断的最终值。

密钥必须通过 Secret、密钥管理服务、部署平台安全变量或受控配置中心注入。密钥轮换不得要求重新构建应用镜像。

## 容器镜像

容器镜像必须使用稳定标签，不得以 `latest` 作为生产发布依据。镜像标签应当包含版本或源码修订标识。

镜像构建必须排除源码仓库中的密钥、测试输出、缓存、本地临时文件和包管理器凭据。镜像运行入口必须可重复、可观测、可停止。

生产镜像必须控制体积和攻击面。调试工具、构建工具和测试夹具不得进入生产镜像，确需排障能力时必须通过受控方式临时启用。

## Kubernetes 资源命名

Kubernetes 资源名称必须采用稳定、可读、可检索的命名方式，例如 `<system>-<component>-<purpose>`。命名不得依赖个人姓名、临时任务编号或含义不明缩写。

资源标签必须至少覆盖应用、组件、环境、版本、团队和管理方式。标签值必须稳定，避免使用高基数字段。

Deployment、Service、Ingress、ConfigMap、Secret、Job 和 CronJob 必须能从名称和标签判断所属系统、环境和用途。

## 落地要求

- 项目必须在运行说明中记录环境、配置来源、密钥注入方式、镜像构建方式和部署资源名称。
- 发布前必须确认镜像、配置、环境和 Kubernetes 资源指向同一版本和同一发布范围。
- 生产问题排查必须能够通过资源名称、标签、镜像版本、结构化日志和指标关联到具体发布。

## 检查清单

- 环境是否明确区分，且不依赖修改源码切换？
- 配置和密钥是否分离？
- 容器镜像是否可追溯到源码和构建信息？
- 镜像是否排除了密钥、缓存和临时文件？
- 生产容器是否遵循最小权限？
- Kubernetes 资源命名和标签是否支持治理和排障？
- ConfigMap 与 Secret 是否职责清晰？
